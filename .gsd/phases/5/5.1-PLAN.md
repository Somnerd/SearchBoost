# Plan 5.1: Backend Session Differentiation

## Objective
Isolate conversation tracking. Enable backend `history.js` and Express Router to create unique `session_id`s appending a `thread_id` rather than binding permanently to just `{username}`. Produce endpoints retrieving a user's isolated threads.

## Tasks

<task type="auto">
  <name>Database Query Evolution</name>
  <files>searchboost_api/src/db/history.js</files>
  <action>
    Modify `history.js` to expose two new functions: 
    1. `getSessions(username)`: `SELECT DISTINCT session_id FROM conversation_turns WHERE session_id LIKE $1` to retrieve list of sessions.
    2. `getHistory(sessionId)`: Filter `content, role, created_at` matching the exact `sessionId`, overriding the previous `SB-SESSION-{username}` generic query.
  </action>
  <verify>List exports in `history.js`.</verify>
  <done>Backend queries support exact `thread_id` isolation.</done>
</task>

<task type="auto">
  <name>API Routing</name>
  <files>searchboost_api/src/routes/search.js</files>
  <action>
    - `/enqueue`: Extract an optional `thread_id` from `req.body` and compile the Node request structure uniquely `session_id = SB-SESSION-${username}-${req.body.thread_id}`.
    - `/sessions`: Define a new endpoint running `getSessions`.
    - `/history/:thread_id`: Extract thread parameter to query explicit conversation arrays. 
  </action>
  <verify>Examine router exports mapping the GET variables.</verify>
  <done>External API fetches the threads individually.</done>
</task>

## Success Criteria
- [ ] No regression on generic `thread_id` defaults if frontend UI hits refresh unmodified.
- [ ] Users can retrieve past active session IDs mapped properly.
